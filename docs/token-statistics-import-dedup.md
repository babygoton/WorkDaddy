# 会话导入后的 Token 重复统计修复

基于 `main` 的 `ad95beb`，分支 `codex/fix-import-token-double-count`。

## 问题与修复范围

导入会话会分配新 ID，跨账号复制也会生成消息文件副本。原统计按文件累加历史 usage，导致没有新模型请求也会增加输入、输出、缓存读写和调用次数。旧的逐文件日汇总缓存已丢失记录身份，不能在汇总后可靠去重。

修复仅改变 `scripts/token-stats.js` 的扫描、缓存和归属解析；`scripts/daemon.js` 的版本从 main 的 1.2.36 升到 1.2.37，并更新 build ID，使启动器能替换旧进程。没有修改会话文件、导入/复制流程、账户切换、积分账单接口或 UI。

## 统计规则

- 对解析后的完整 JSON 记录计算 SHA-256。副本中相同历史记录跨文件只统计一次，不仅按请求 ID 或 Token 数值去重，因此一个请求的不同记录、相同用量的不同调用仍分别计数。
- 相同记录在一个文件中出现多次时保留出现次数；其他文件的对应出现位置视为副本。这个规则针对当前导入/复制保留原消息内容的行为，不改变单文件内部的统计口径。
- 副本新增的消息单独计数。先跨文件去重，再应用账号、模型和日期筛选。
- 账号优先使用消息内明确的账号，其次使用原始 `sessionId` / `conversationId` 对应的账号。没有原始会话字段时保留文件归属回退；若同一记录的副本归属冲突，则只计入总量，不猜测归属。原始会话字段存在但该会话的归属已不可查时，也不把历史用量算到副本持有账号。
- 缓存版本升为 8，旧版本自动全量重建。按文件保存摘要和用量元数据，未变更文件不会因切换筛选条件而重新读取；账号归属使用最新映射，不固化在旧缓存中。缓存和 API 结果不包含消息正文或原始请求/消息 ID。
- 删除或更新副本后按现存文件重新合并；不保留已经没有任何文件承载的用量。没有时间戳的旧记录仍采用扫描时间回退，但重复导入优先保留较早的缓存观测日期。

## 验证（2026-09-14）

- 先写测试再修复：最初 8 项新增测试在 main 上有 7 项失败；修复后增加 AI 格式和无时间戳记录场景，共 10 项新增测试通过。原有 9 项 Token 测试全部通过。
- 导入集成测试执行真实加密解包、附件恢复、SQL 构造和复制函数，仅将数据库执行替换为内存账号映射。连续导入三次再跨账号复制，原本 100 个输入 Token 始终为 100；所有导入文件和原文件逐字节一致。
- 验证继续聊天、同请求多条记录、相同用量的不同调用、旧格式、删除副本、缓存重建、账号映射变化、快照与 subagents 排除、今天及 7/30/90 天、模型与账号筛选。
- 用 12,000 条无副本的虚构调用做 24 组新旧差分比较，冷扫描和缓存扫描在 4 个日期范围及账号/模型筛选下结果一致。
- 同一数据复制成 60,000 行，仍只统计 12,000 次；本机测得冷扫描约 263ms、缓存扫描约 106ms，缓存约 15.8MiB。身份元数据增加了缓存体积；这些数字是一次本机测量，不是所有设备的性能保证。
- 纯 Git worktree 的全量测试因缺少被 Git 忽略的 `WorkDaddy.app/Contents/MacOS/launcher` 失败；未修改 main 的独立临时检出同样失败。随后在临时目录放入完全相同的修复源码及现有未修改 launcher 作为测试夹具，使用 Node 26.8.1：720 项中 712 通过、0 失败、8 项 Windows 环境相关跳过。
- `node --check` 覆盖统计模块、daemon、inject、win-launcher、watchdog；`git diff --check` 通过。

未执行 Windows 实机安装/更新或真实 WorkBuddy 导入操作，未重启正在运行的 daemon/WorkBuddy，未修改或打包 app。积分接口未发现由导入导致重复扣款的证据，本修复不修改官方账单。
